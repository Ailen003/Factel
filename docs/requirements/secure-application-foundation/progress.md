## Current State

H2C-2b is implemented in code. Its bounded scope is owner-only recovery of an operator's lost MFA, a dry-run-first operational break-glass command for total owner-factor loss, and a two-participant ownership-transfer protocol. H3 and password-plus-MFA recovery remain excluded. The new additive migration is prepared and verified but has not been applied without direct immediate user confirmation; no real recovery or ownership transfer has run.

H2C-2a is implemented, migrated and active. Read-only `prisma migrate status` reports all ten existing migrations applied and the database schema up to date. Aggregate checks found three administrators, exactly one active owner, that owner MFA-ready, no invalid role/profile combination, no inactive owner, no administrator missing a credential or active workspace, and no divergence between `twoFactorEnabled` and the verified Better Auth factor row. Identities, emails, IDs, factors, tokens and sessions were intentionally excluded from the evidence. H2C-2a's destructive real-factor journey remains outside this iteration unless separately authorized.

`modules/users` remains the primary reference: feature folders contain presentational components and RHF/Zod containers; localized schema factories are reused at thin server-action boundaries; hooks own pending/error/result state; server-only services reload authoritative capability and target state, use typed `ServiceResponse` results, advisory locks, serializable Prisma transactions, operation/version fences, atomic session revocation and mandatory safe audit. `modules/two-factor` supplies the sensitive TOTP field, Better Auth error mapping and official factor boundary. The proposed structure adds `mfa-recovery/` and `ownership-transfer/` UI features under `modules/users`, shared schemas/types/actions/hooks/services under its existing `lib/` anatomy, and an authentication-infrastructure break-glass service plus script/runbook outside web actions. Reused pieces include `requireAdminCapability`, current-session reload, the credential-mutation advisory-lock pattern, `writeAuthAudit`, shared modal/design-system fields and the list/detail action seams. Necessary deviations are security-driven: step-up remains server-only and calls Better Auth 1.7.3 `verifyPassword` plus session-context `verifyTOTP` with `trustDevice: false`; break-glass has no web surface; recipient accept/decline authorization is request-specific rather than a general owner-management capability; and all factor deletion is application-owned transactional persistence because Better Auth's normal disable endpoint requires the target's password and rotates its session.

H2C-1 is implemented and verified. The product keeps general roles `trial_user` and `platform_admin` and adds nullable `adminProfile`: trial users require null, while administrators require a consistent `owner` or `operator` profile to exercise administrative capabilities. A centralized typed server-only matrix and `requireAdminCapability` resolve the active session, then reload current role, profile and status authoritatively for every request. Missing or inconsistent profiles fail closed; browser-facing Better Auth administrative permissions remain empty. Existing sessions therefore lose privileged access immediately after degradation or suspension.

The H2C-1 seed follow-up declared the explicitly configured `SEED_ADMIN_EMAIL` fixture as `platform_admin/owner`, while trial fixtures remained profile-null. Reruns are idempotent for the same owner, refuse to replace a different owner or an existing operator profile, revoke stale sessions on the legacy null-to-owner transition and record a secret-free profile mutation plus audit event. That iteration performed only a database-free dry-run. Subsequent read-only evidence now confirms the H2C-1 migration is applied and a valid active owner exists without establishing whether a seed or bootstrap created it.

The owner has every operator capability plus administrator management, contact-email updates, admission resume and future global-limit/global-reopen controls. Operators may list and manage trial users, create trials, reissue credentials, confirm delivery, suspend/reactivate, revoke sessions, perform permitted trial deletion, read required Settings state and pause admission. They cannot act on administrators, promote themselves, change profiles, modify contact email or resume admission. Each service/action authorizes its exact capability on the server; UI-derived capability flags only reduce confusion.

Owner-only promotion and demotion require confirmation, expected-version/idempotency fencing, a per-target advisory lock, serializable mutation, session revocation and mandatory fail-closed audit. Demotion stops before partial mutation when the resulting trial identity/workspace would violate existing invariants. The sole owner cannot be demoted, suspended or deleted, and no web ownership-claim or transfer action exists. Settings separates contact update, pause and resume into independently authorized operations with version fencing and transactional audit.

The explicit `pnpm auth:bootstrap-owner --email <email>` command accepts only an existing active `platform_admin`, defaults to a non-mutating dry-run, requires `--confirm` for mutation and additional production confirmation, serializes single-owner creation, is idempotent for the same owner, rejects a different existing owner, assigns remaining legacy administrators as operators, revokes affected sessions and audits safe identifiers only. It was not executed during its implementation iteration. Current read-only status now reports `20260910210000_admin_profiles` applied and a valid active owner; owner provenance is intentionally not inferred.

H2C-2a has completed code verification for privileged TOTP enrollment, backup codes and the second-factor login challenge. Its migration is applied and the schema is current; only the authorized real PostgreSQL journey remains pending. H2C-2b implements administrative MFA recovery and protected ownership transfer in code with an additive eleventh migration prepared but not applied. H2 and REQ-001 remain in progress and are not complete.

H2B delivery acknowledgment is repaired and its existing deferred-confirmation intent is complete. The reported immediate `DELIVERY_CONFIRMATION_FAILED` was reproduced safely against the applied local database: Prisma 7.10.0 with `adapter-pg` rejected the PostgreSQL `void` result from `SELECT pg_advisory_xact_lock(...)` as P2010 `UnsupportedNativeDataType`. Casting the advisory-lock result to text preserves the same serialization boundary and allows the conditional delivery update and mandatory audit to complete. Diagnostic execution was rollback-only; it persisted no test data and confirmed that the affected issuance remained issued and undelivered.

An authorized administrator can now acknowledge a current issued-but-undelivered credential later from the quick-action menu or user detail. This transition confirms the existing issuance and general delivery channel; it does not reissue a credential and never retrieves, persists or redisplays the secret. The same RHF/Zod delivery form serves immediate and deferred acknowledgment, and the action is offered only when the current issuance and user version match. Safe failure logging includes only a validated Prisma `P####` code, never message, metadata or secret.

H2B enables a server-authorized platform administrator to reissue an activation credential for a never-activated trial user or reset access with a recovery credential for an activated trial user. The action requires explicit confirmation and a bounded structured reason, revokes every target session, keeps suspended accounts suspended, exposes the generated credential only in the immediate successful response, and records issuance, supersession and optional delivery acknowledgment without the secret or private channel details. Activation retains null trial timestamps until H2A replacement starts the 14-day clock once; recovery preserves `trialActivatedAt`, `trialExpiresAt`, workspace and credits exactly.

A dedicated secret-free issuance ledger and `User.temporaryCredentialVersion` fence distinguish prepared, issued, superseded and failed attempts. A unique operation UUID prevents replay; expected-version checks reject stale intent; one current issuance per target and a shared PostgreSQL session advisory lock serialize H2A/H2B Better Auth mutations through finalization. Preparation expires the temporary gate and revokes sessions before provider mutation. Better Auth or mandatory-audit failure returns no secret and leaves the account blocked and repairable by a later intentional `failure_recovery`. Delivery acknowledgment stores only the general category (`in_person`, `phone`, `secure_message` or `other`), actor and time. Closing without acknowledgment leaves the record issued and undelivered.

The H2B regression iteration observed eight applied migrations at that time and required no schema change. Current H2C-2a baseline evidence supersedes only the live status: all nine migrations through `20260910210000_admin_profiles` are now applied.

Previous review iteration: H2A distinguishes activation and recovery-purpose credentials. Recovery replacement preserves the original trial dates, and PostgreSQL requires activation/expiry timestamps to be both absent or both present. Administrative creation accepts no password input; the Node.js cryptographically secure random source creates a 192-bit password that is passed to Better Auth and displayed once only after audited provisioning succeeds. Direct Better Auth HTTP-handler and post-password-change partial-failure regressions are covered.

Current H2 foundation: administrator provisioning issues a 72-hour temporary credential and marks each new trial account for mandatory replacement. Authoritative session, workspace and action boundaries reject pending or expired credentials; the only exposed operations are minimal activation state, the application-owned password replacement flow and sign-out. Successful Better Auth password replacement serializes per user, clears the temporary state exactly once, starts the 14-day trial clock, revokes other sessions and records safe audit metadata. The responsive experience and administrator state indicators have ES/EN parity. Existing accounts remain non-retroactive and the seed explicitly marks its fixtures activated without extending them on rerun. H2B recovery/reset and delivery acknowledgment are verified with their migration applied; H2C-1 administrative profiles/capabilities and H2C-2a MFA are verified with their migrations applied. H2C-2a still awaits its authorized real journey, while H2C-2b recovery and ownership transfer are code-complete and await the eleventh migration plus authorized operational verification.

Previous H1 iteration: the database-backed access-contact email, admission switch, administrator settings surface and bilingual landing mailto form are operational; its migration is applied and the current environment has a configured contact plus enabled requests. Human mailbox monitoring, request review, account provisioning and private credential delivery remain manual operations.

Current policy baseline: manual admission starts at the landing contact and ends in an individual administrator-created account with mandatory temporary-password replacement. H2B records only a general delivery category while the human private-channel procedure remains an operational choice. H2C-2a mandatory administrator MFA is migrated. H2C-2b controlled recovery and protected ownership transfer are implemented in code and await migration plus authorized operational verification.

Prisma-backed user administration records initial locale and credit allocation, permits locale edits, activates or suspends authorized trial accounts, automatically revokes sessions on suspension, supports explicit session revocation, and deletes identity-only trial accounts after confirmation. Capability policy prevents operators from acting on administrators and protects the sole owner from demotion, suspension or deletion. Account deletion is transactional and preserves detached audit proof; it stops without mutation when any workspace-owned or user-referenced domain data exists, leaving cross-domain cleanup to REQ-007. Browser-facing Better Auth roles expose no generic password/session administration: application-owned server services call Better Auth and direct HTTP administrative endpoints remain denied. Public registration, automated invitations, public email recovery and magic links remain deferred. H2B, H2C-1 and the H2C-2a migration are active; H2C-2a still needs its authorized real journey. H2C-2b recovery/ownership transfer is implemented in code but its additive migration and real operations remain unapplied/unexecuted, so REQ-001 and H2 stay in progress.
